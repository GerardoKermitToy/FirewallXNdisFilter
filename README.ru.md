# FirewallXNdisFilter

[English](README.md) | **Русский**

FirewallXNdisFilter — экспериментальный сетевой фильтр для Windows, написанный на Rust, с монитором и клиентскими API на C++. Он использует **облегчённый фильтр NDIS (Lightweight Filter, LWF)** на совместимых физических и виртуальных Ethernet-адаптерах хоста.

Проверяться может только трафик, проходящий через подключённый модуль NDIS. Некоторые адаптеры не поддерживают подключение обычного LWF; например, адаптеры Wintun/WireGuard, объявляющие `LowerRange=nolower`, не поддерживаются. Внутренний трафик между виртуальными машинами, не проходящий через подключённый адаптер хоста, также находится вне области действия фильтра. Версия пакета и API устройства — **0.3.3.0**; используйте соответствующие друг другу драйвер и клиент.

> **Предупреждение:** это экспериментальное программное обеспечение уровня ядра. Смешанные IP NBL с локальными и транзитными пакетами разделяются: локальные пакеты обходят политику, а для транзитных принимаются независимые вердикты или резервные решения. При подключённом контроллере драйвер пытается поставить в очередь одно предупреждение. Если список локальных адресов недоступен, политика временно не применяется. **Весь трафик к multicast-адресам IPv4 и IPv6 обходит политику при любом TTL/Hop Limit** на каждом подключённом адаптере, в том числе если пакет может достичь гостевой системы. Также действуют описанные ниже исключения для broadcast и DHCP. Эти исключения не проверяют подлинность отправителя и не защищают от подмены адресов. В остальных случаях при отсутствии контроллера политика по умолчанию работает по принципу fail-closed и отбрасывает подходящий транзитный IP-трафик на подключённых адаптерах. Используйте тестовую машину с возможностью локального восстановления; автономные тесты и включённые привязки не доказывают правильность фильтрации в рабочей системе.

## Сборка

Требования:

- Windows x64 сборки **25341 или новее** и совместимые Ethernet-адаптеры для фильтрации трафика NDIS.
- Инструменты Visual Studio C++ x64, CMake и Ninja; Rust 1.91+ с целевой платформой `x86_64-pc-windows-msvc`.
- Windows SDK и WDK **10.0.28000.0**, а также LLVM с libclang. Укажите `LIBCLANG_PATH`, если libclang отсутствует в `%ProgramFiles%\LLVM\bin`.
- Сертификат подписи и корневой сертификат. В [инструкции по созданию сертификатов windows_kext_mod](https://github.com/GerardoKermitToy/windows_kext_mod#1-create-the-local-certificates) описано создание локальных ключей, используемых в примере ниже. Не помещайте закрытые ключи в систему контроля версий.

Выполните в Git Bash из корня репозитория сборку подписанного пакета Release и автономные тесты:

```bash
powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File scripts/Build.ps1 -Test -PfxPath 'C:\portmaster_v3\windows_kext\localhost-km.pfx' -RootCertificate 'C:\portmaster_v3\windows_kext\localhost-root-ca.der'
```

Укажите пути к сертификатам для вашей машины. При необходимости задайте `FIREWALLXNDISFILTER_PFX_PASSWORD` или передайте `-PfxPassword`. По умолчанию сборка запрашивает метку времени RFC 3161 у `http://timestamp.digicert.com`; для другого сервиса используйте `-TimestampUrl`. Отправляется только хеш для метки времени; закрытый ключ остаётся на локальной машине. Подпись сама по себе не гарантирует, что Windows примет драйвер: отдельно проверьте требования к подписи и безопасности целевой системы. Сборка не устанавливает драйвер и не изменяет хранилища сертификатов или параметры безопасности.

Пакет в `dist/` содержит `FirewallXNdisFilter.sys`, соответствующие INF и CAT, `FirewallXNdisFilterNotify.dll`, `ndis_monitor.exe`, `Install.exe`, `Uninstall.exe` и соответствующие полные PDB. Храните эти файлы вместе и не смешивайте версии пакета. Если `dist/` содержит артефакты другого продукта или монитора с другим именем, сборка откажется их смешивать; сохраните и переместите несовместимый пакет перед повторной сборкой.

## Установка

Используйте консоль с повышенными правами Administrator/SYSTEM, остановите все экземпляры монитора и обеспечьте возможность локального восстановления. Во время установки Windows может изменить сетевую конфигурацию. Если фильтр уже установлен, сначала удалите его соответствующей программой удаления; установщик не заменяет работающий драйвер и не перезаписывает регистрацию notify-компонента, принадлежащую другому продукту.

```bash
./dist/Install.exe
```

Установщик использует пакет рядом с EXE и включает подходящие пути привязки, предоставляемые NetCfg для этого фильтра, включая совместимые физические Ethernet-адаптеры и виртуальные сетевые адаптеры хоста. Адаптер без совместимого пути привязки не охватывается фильтром. Автоматическое включение новых адаптеров не гарантируется; прежде чем рассчитывать на их фильтрацию, проверьте привязку и работающий модуль. Используйте `--what-if` для предварительной проверки без изменений или `--yes`, чтобы пропустить подтверждение. Конфликтующие подготовленные пакеты могут привести к ошибке установки; вместо перезаписи файлов пакета используйте соответствующую программу удаления.

Если установка возвращает **3010**, перезагрузите систему и затем возобновите включение доступных на тот момент совместимых путей NetCfg:

```bash
./dist/Install.exe --enable
```

## Монитор

Начните с политики PermanentAccept по умолчанию:

```bash
./dist/ndis_monitor.exe --duration 15 --timestamps --memory-stats --out allow.log
```

Не указывайте `--duration`, чтобы монитор работал до нажатия **Ctrl+C**. Чтобы применить блокирующий вердикт только к тестовой удалённой конечной точке:

```bash
./dist/ndis_monitor.exe --duration 10 --match 192.0.2.10:9000 --verdict permanent-block --out block.log
```

`--match` выбирает удалённую конечную точку, сообщаемую драйвером, в обоих направлениях; события, не соответствующие условию, получают PermanentAccept. `--filter-ip` только скрывает вывод и не ограничивает применение вердиктов. Блокирующий вердикт без `--match` применяется ко всем событиям и может нарушить сетевое соединение. Остальные параметры описаны в выводе `./dist/ndis_monitor.exe --help`.

Монитор открывает существующее устройство управления; он не устанавливает, не загружает и не привязывает драйвер, а также не запускает временный драйвер. Перед запуском монитора установите и запустите NDIS LWF. Параметр `--duration` ограничивает время мониторинга, но не установки или запуска драйвера.

При запуске монитор выводит снимок подключённых адаптеров и количество работающих модулей NDIS; количество обновляется с интервалом `--poll`. Это диагностические данные NDIS, а не доказательство перехвата трафика. При недоступности запроса выводится предупреждение, а не выдуманный пустой результат.

## Удаление

Остановите монитор и выполните в консоли с повышенными правами:

```bash
./dist/Uninstall.exe
```

Программа удаления снимает разрешение на привязку и удаляет этот фильтр и обнаруженные пакеты его драйвера, даже если целевые адаптеры уже отсутствуют. `--what-if` перечисляет затрагиваемые пакеты без изменения состояния системы. Если удаление возвращает **3010**, перезагрузите систему и повторно запустите `Uninstall.exe` перед повторной установкой.

## API

Многократно используемые клиенты — [PortmasterKext.h](monitor/include/PortmasterKext.h) (`pmkext`, с [DriverProtocol.h](monitor/include/DriverProtocol.h) для кодека) и независимый C++20-клиент [FirewallXNdisFilter.hpp](monitor/include/FirewallXNdisFilter.hpp) (`firewallxndisfilter::Client`). Определения формата обмена на стороне драйвера находятся в [protocol/src/lib.rs](protocol/src/lib.rs); для снимков адаптеров используется [adapter_info.rs](driver/src/adapter_info.rs).

Полный пример использования клиента из одного заголовочного файла (header-only) приведён в [callback_client.cpp](monitor/examples/callback_client.cpp). Он подключается к существующему устройству, разрешает события соединения и работает в течение десяти секунд после запуска. Этот клиент не устанавливает и не загружает драйвер; его `Open()` может неограниченно долго ожидать запуска драйвера, как описано ниже.

### Семантика

- **В ConnectionIpv4/ConnectionIpv6 нет поля `process_id`.** Поле `interface_index:u32` после `id` обозначает адаптер хоста в точке перехвата (`BaseMiniportIfIndex`), а не интерфейс внутри гостевой системы. Оно сохраняется с каждым ожидающим пакетом и группой данных о трафике, поэтому перемежающийся трафик разных интерфейсов сохраняет собственный индекс. Поля compartment/sub-interface ID, TID, switch/port/GUID/LUID отсутствуют; принадлежность процессу хоста или отдельной ВМ не определяется. Индексы интерфейсов могут изменяться или использоваться повторно после пересоздания адаптера и не являются постоянными идентификаторами. В совместимых типах `ConnectionEnd` есть поле PID, но этот драйвер не генерирует такие события.
- `direction=0` обозначает приём NDIS хостом, а `direction=1` — отправку NDIS хостом. На виртуальном адаптере хоста, обращённом к гостевой системе, они обычно соответствуют исходящему и входящему трафику гостевой системы соответственно; на других адаптерах эти значения нельзя считать доказательством принадлежности гостевой системе. `local_*` — наблюдаемый IP-адрес источника при приёме и назначения при отправке; `remote_*` — противоположная конечная точка. На каждом интерфейсе консоль использует те же направления, конечные точки и счётчики трафика, что и низкоуровневый API.
- Одно событие соединения и его `id` представляют **один ожидающий NBL**, а не сокет или время жизни соединения. Однородный NBL с несколькими NB имеет один вердикт и содержит полный IP-пакет из первого NB, а не объединение всех NB. Смешанный локальный/транзитный NBL вместо этого разделяется на отдельные дочерние NBL с независимым владением — по одному для каждого NB; для транзитных дочерних элементов принимаются независимые решения политики с отдельными событиями, когда требуется вердикт. Состоящие только из транзитного трафика NBL с несколькими NB, обрабатываемые политикой, допускаются только для TCP/UDP-пакетов с полностью определёнными и совпадающими ключами нефрагментированных потоков; несовместимые транзитные потоки, некорректные NBL, фрагменты, NBL с неполными ключами потоков и NBL, содержащие пакеты других IP-протоколов, отбрасываются. NBL с одним NB, содержащие пакеты других IP-протоколов, по-прежнему обрабатываются обычной политикой.
- `payload_layer=3`. `payload` содержит **полный наблюдаемый IP-пакет**, включая заголовки IP/транспортного уровня, без заголовков Ethernet/VLAN и дополнения Ethernet. `payload_size` — его полная длина в байтах. Нормализация конечных точек не изменяет байты пакета. Для LSO/RSC это логический пакет, наблюдаемый на уровне NDIS, не обязательно один кадр в сети.
- Обычно для политики выбираются только пакеты, у которых наблюдаемые адреса источника **и** назначения отсутствуют в общесистемном списке локальных одноадресных и anycast IPv4/IPv6-адресов, с учётом описанных ниже исключений. Пакет, у которого хотя бы один адрес присутствует в списке, обходит события вердиктов, кэш и учёт трафика, в том числе при отсутствии контроллера. Адреса сравниваются глобально между адаптерами; адаптер с адресом не обязательно должен быть подключён к этому фильтру. Пока список недоступен или перестраивается, политика временно не применяется, а неизвестные адреса не считаются транзитными. Одноадресные уведомления NETIO асинхронны; anycast опрашивается с номинальным интервалом пять секунд, поэтому изменения адресов учитываются не мгновенно.
- Все пакеты с multicast-адресом назначения IPv4 `224.0.0.0/4` (от `224.0.0.0` до `239.255.255.255`) или IPv6 `ff00::/8` обходят вердикты, кэш и учёт трафика при **любом TTL/Hop Limit** на всех подключённых адаптерах, включая обращённые к гостевым системам. Решение использует только семейство IP и адрес назначения, независимо от адреса источника, транспортного протокола, портов, содержимого, состояния контроллера и списка локальных адресов. Оно охватывает все области и флаги IPv6, фрагменты и пакеты с offload; mDNS, IGMP, MLD и DHCPv6 multicast — лишь примеры разрешённого трафика. Принадлежность к группе и подлинность отправителя не проверяются. Обычный парсер с проверкой границ, проверки метаданных и владения NDIS, а также проверка приостановки подключения сохраняются: отклонённые ими пакеты отбрасываются, но драйвер не проверяет корректность содержимого всех протоколов.
- Ограниченный broadcast IPv4 (`255.255.255.255`) также обходит политику независимо от списка адресов при TTL **1**. При другом TTL действуют описанные ниже исключения DHCP и обычные правила списка адресов и политики. Направленный broadcast подсети не определяется без её префикса.
- IPv4 UDP-пакеты от `0.0.0.0:68` к ограниченному широковещательному адресу `255.255.255.255:67` обходят вердикты, кэш и учёт трафика при **любом TTL**, включая 255. Это покрывает адреса и порты DHCP Discover, но драйвер проверяет только адреса, порты и протокол, а не содержимое UDP: другие сообщения с теми же адресами и портами тоже подпадают под исключение. Фрагменты без проверенных портов обрабатываются по другим правилам выше. Обычное исключение для ограниченного broadcast по-прежнему действует на весь IPv4-трафик с TTL 1.
- IPv4 UDP-пакеты сервера с порта `67` на порт `68` к ограниченному широковещательному адресу `255.255.255.255` обходят вердикты, кэш и учёт трафика при **любом TTL**, независимо от адреса источника и содержимого UDP. Содержимое не проверяется: исключение включает и другие сообщения, а также пакеты с offload, соответствующие этим адресам и портам, а не только DHCP.
- Остальные IPv4 UDP-пакеты с адресом назначения вне multicast и с порта `67` на порт `68` обходят политику при **любом TTL**, если они являются ответами DHCP Offer или ACK. После того как список локальных адресов определил пакет как транзитный, драйвер проверяет ответ BOOTP, сигнатуру DHCP, единственную option 53 длиной 1 со значением 2 (Offer) или 5 (ACK) и корректность опций вплоть до End. Фрагменты и пакеты с offload сегментации или объединения под это исключение с проверкой содержимого не подпадают.
- IPv6 UDP-пакеты с адресом назначения вне multicast и с серверного порта `547` на клиентский порт `546` обходят политику при **любом Hop Limit**, если тип сообщения DHCPv6 — 2 (Advertise) или 7 (Reply). После определения пакета как транзитного драйвер проверяет четырёхбайтовый заголовок сообщения и длины опций в пределах UDP-датаграммы. Поддерживаемые заголовки расширений IPv6 учитываются в пределах ограниченного префикса парсера; пакеты, чьи порты UDP недоступны в этом префиксе, фрагменты и пакеты с offload сегментации или объединения под это исключение с проверкой содержимого не подпадают. DHCPv6 Reply включает не только ответы о выдаче адреса.
- Исключения DHCP не проверяют подлинность сервера и соответствие ответов запросам клиента. За пределами более широких исключений для multicast и broadcast фрагменты без проверенных портов и нераспознанные или неполные ответы обрабатываются по обычным правилам. Проверка DHCP не выходит за границы объявленной UDP-датаграммы.
- **Смешанные локальные/транзитные NBL:** после того как каждый NB успешно обработан парсером с проверкой границ, драйвер пытается выдать одно предупреждение с индексом интерфейса и разделяет NBL на дочерние элементы с независимым владением. Локальные пакеты обходят политику; каждый транзитный пакет проходит обычную обработку вердикта/резервного решения и учёта трафика без использования или заполнения постоянного кэша. Исходный NBL возвращается только после завершения всех дочерних элементов, без изменения его цепочки NB. Обычные дочерние элементы отправки/приёма используют клонированные дескрипторы NB/MDL, ссылающиеся на данные исходного пакета без дополнительного копирования при разделении; пакет приёма с `RESOURCES` сначала полностью копируется. События соединения по-прежнему копируют содержимое пакета. Локальные и транзитные дочерние элементы могут завершиться в другом порядке. Некорректные пакеты, смеси IP и не-IP, неподдерживаемые метаданные или флаги NBL и приостановленные подключения по-прежнему приводят к отбрасыванию.
- Не-IP-трафик, например ARP, не создаёт событий соединения и пропускается, если поддерживаются его владение и профиль. При попадании в кэш обработка выполняется в ядре без нового события вердикта.
- Вердикты Redirect, UpdateV4/V6, приостановка по PID и IOCTL для идентификатора потока **не поддерживаются**. Некоторые имена перечислений остаются в заголовке C++ только для совместимости исходного кода.
- NDIS не предоставляет уведомлений о закрытии сокета/ALE. **События Connection-END никогда не генерируются**, в том числе при истечении срока кэша, тайм-ауте или отключении.
- Один пакет, проходящий через несколько подключённых адаптеров, может вызвать отдельные вердикты и подсчёты трафика в каждой точке наблюдения. Успешная запись вердикта не подтверждает доставку.
- NDIS поддерживает объединение принимаемых UDP-пакетов и распознаёт разгрузку сегментации UDP; такие логические пакеты не кэшируются.

Размер содержимого соединения ограничен **1 МиБ (1048576 байт)**; этого достаточно для обычных пакетов IPv4/IPv6 и поддерживаемых более крупных пакетов с разгрузкой. Более крупные логические пакеты отбрасываются, а не передаются с усечённым содержимым. За исключением указанного ниже ограничения LogLine, драйвер не задаёт совокупного лимита байтов или количества элементов для записей пакетов, метаданных, очередей, контекстов NBL и частных копий при приёме. Исчерпание невыгружаемого пула памяти драйвера может вызвать аварийную остановку системы; клиенты должны своевременно забирать записи. Пока контроллер подключён, некорректные или неподдерживаемые пакеты, ошибки копирования/ресурсов, неудачные отправки и приостановленные интерфейсы создают предупреждающие записи LogLine, если их удаётся поставить в очередь; тайм-ауты вердиктов и обычные блокирующие вердикты таких записей не создают. Сохраняется до **1000 записей LogLine в очереди** любого уровня важности, включая частично прочитанную запись; при достижении предела каждая новая запись LogLine заменяет самую старую полностью непрочитанную запись LogLine. Частично прочитанная запись всегда дочитывается до конца для сохранения границ записей в потоке. На события соединения и отчёты о трафике это ограничение не распространяется. При отсутствии контроллера записи LogLine не сохраняются; ошибка очереди или выделения памяти может помешать созданию записи. `--filter-pid` не поддерживается.

Это экспериментальный код уровня ядра. Автономные тесты и включённая привязка не доказывают правильность фильтрации в рабочей системе.

### Сеанс устройства и IOCTL

Откройте **`\\.\FirewallXNdisFilter`** от имени Administrator/SYSTEM с `GENERIC_READ | GENERIC_WRITE`, `OPEN_EXISTING` и эксклюзивным доступом. Клиент C++ использует `FILE_FLAG_OVERLAPPED`; буферизованные чтения ненулевой длины ожидают байты событий и могут быть отменены. Устройство может удерживать только **один контроллер**.

Открытие устройства активирует сеанс политики и сбрасывает его очередь событий, постоянный кэш и накопители трафика. Прежде чем полагаться на протокол, клиент должен проверить версию устройства. `Driver::Open` только открывает сеанс; монитор отдельно проверяет версию.

Все поддерживаемые IOCTL используют `CTL_CODE(40000, function, METHOD_BUFFERED, FILE_READ_DATA | FILE_WRITE_DATA)` и не принимают входной буфер:

| IOCTL | Функция / числовой код | Результат и действие |
|---|---|---|
| `IOCTL_VERSION` | `0x800` / `0x9C40E000` | Ровно четыре байта: `00 03 03 00`. Выходной буфер должен содержать не менее четырёх байт. |
| `IOCTL_SHUTDOWN` | `0x801` / `0x9C40E004` | Без выходных данных. Деактивирует сеанс политики, отбрасывает события в очереди, кэш и данные трафика и обрабатывает ожидающие пакеты согласно настроенному резервному решению. Не выгружает, не отвязывает и не удаляет LWF. |
| `IOCTL_FILTERED_DEVICE_COUNT` | `0x802` / `0x9C40E008` | Ровно четыре байта: беззнаковое 32-битное число работающих модулей фильтра NDIS в порядке little-endian. Выходной буфер должен содержать не менее четырёх байт; входные данные должны отсутствовать. Не влияет на политику или привязки. |
| `IOCTL_ADAPTER_INFO` | `0x803` / `0x9C40E00C` | Версионированный снимок каждого подключённого модуля, включая неработающие, с идентификатором адаптера хоста, именами, MAC-адресом, состоянием соединения и общими атрибутами NDIS. Входные данные отсутствуют; выходные данные имеют переменный размер, при `STATUS_BUFFER_OVERFLOW` возвращается 16-байтовый заголовок для определения размера. Оба клиента увеличивают буфер по мере необходимости. Не имеет побочных эффектов для политики, операций OID или привязок. |

Учитываются только модули, допущенные проверкой ядра, успешно перезапущенные и ещё не начавшие приостановку. Модули, которые лишь настроены, отклонены, подключены, но приостановлены, не перезапустились или отключены, не учитываются. Приостановка немедленно исключает модуль из счётчика, даже пока завершается обработка незавершённых NBL; последующий успешный перезапуск добавляет его обратно. Снимок не зависит от состояния сеанса политики контроллера, поэтому shutdown не сбрасывает его. Он описывает активный перехват на адаптерах, а не доставку пакетов, сетевое соединение или факт наблюдения трафика. При опросе кратковременные переходы могут быть пропущены.

Все остальные IOCTL не поддерживаются. После shutdown закройте дескриптор и откройте его заново для активации нового сеанса. Закрытие активного дескриптора также отключает контроллер и завершает обработку ожидающих решений. Сам по себе shutdown не закрывает дескриптор и не останавливает цикл чтения пользовательского приложения.

Чтения возвращают поток байтов событий без ограничения размера со стороны драйвера, кроме длины запроса Windows **DWORD/u32**. Чтение может завершиться с более чем 65536 байтами и объединить несколько записей; оно может вернуть меньше байтов, чем запрошено. Чтение ненулевой длины ожидает появления байтов и никогда не завершается успешно с пустым результатом только из-за пустой очереди. Запросы нулевой длины по-прежнему возвращают ноль байтов. Для ожидающих чтений нет фиксированного ограничения числа запросов или бюджета байтов; Windows всё равно должна выделить ресурсы буферизованного ввода-вывода. Shutdown, очистка и выгрузка отменяют ожидающие чтения; новые чтения после shutdown сеанса завершаются ошибкой до закрытия и повторного открытия. `CancelIoEx` отменяет ожидающее чтение, но отмена может происходить одновременно с успешным завершением. Всегда дождитесь окончательного завершения незавершённой операции OVERLAPPED, прежде чем освобождать её буфер/событие. Чтение может разделить запись; сохраняйте неполные байты между чтениями. Задержка для опроса чтения не требуется.

### Снимок информации об адаптерах

`IOCTL_ADAPTER_INFO` — дополнительная диагностическая возможность: версия формата событий/команд — **0.3.3.0**. Не определяйте доступность снимка только по версии событий; неподдерживаемый/неудачный запрос считайте **недоступным**, а не пустым списком адаптеров. При запуске, после проверки версии устройства, монитор один раз выводит этот снимок с учётом `--out` и `--timestamps`. При ошибке запроса он предупреждает и продолжает мониторинг. Отдельный счётчик работающих устройств по-прежнему обновляется с интервалом `--poll`; два запроса могут отражать разные моменты времени.

Снимок перечисляет только модули, прошедшие проверку допуска подключения Ethernet с активной конфигурацией схемы 4, а не все адаптеры Windows или настроенные привязки. Подключённый модуль остаётся в списке, пока он изначально приостановлен, приостанавливается или после неудачного перезапуска; флаг `Running` означает, что допуск для него открыт. Отключённые модули исчезают. `module_id` — временный внутренний идентификатор модуля, отличный от любых индексов интерфейсов/LUID Windows. Идентификаторы интерфейсов описывают **стек NDIS хоста**, а не адаптеры гостевых систем, порты коммутатора или принадлежность ВМ. GUID/LUID используются только для диагностики и не расширяют разрешения на привязку.

Драйвер копирует имена и текущий MAC-адрес при подключении, сохраняет общие атрибуты, переданные при успешном перезапуске, и обновляет состояние/скорости соединения по действительным уведомлениям `NDIS_STATUS_LINK_STATE`. Поля содержат **последние значения, предоставленные NDIS**, а не результат нового опроса оборудования/OID. При новом перезапуске необязательные общие атрибуты сначала очищаются; если они не предоставлены, эти значения равны нулю, а `GeneralAttributesValid` не установлен. Флаг наличия базового разъёма доступен только при версии подключения 4. `LinkStateValid` указывает, что флаги автосогласования были предоставлены уведомлением о состоянии соединения; первоначальные состояние подключения/дуплекса и скорости уже получены при подключении. Скорости указаны в бит/с; `UINT64_MAX` означает неизвестное значение согласно соглашению NDIS. `PauseValid` сообщает последнюю наблюдавшуюся причину/флаги приостановки, даже после перезапуска. Возможности с указателями, дескрипторы/адреса ядра, IP-конфигурация, маршруты, идентификаторы процессов/гостевых систем и произвольные данные OID не экспортируются.

Ответ **не является записью события**. Его явный байтовый кодек — [adapter_info.rs](driver/src/adapter_info.rs); не сериализуйте нативные структуры. Все целые числа и кодовые единицы UTF-16 имеют порядок little-endian. Первые 16 байт — четыре значения `u32`:

| Смещение | Поле | Значение |
|---:|---|---|
| 0 | Версия схемы | `1`, независимо от версии устройства/событий. |
| 4 | Размер записи | `1760` байт. |
| 8 | Количество подключённых модулей | `u32`; фиксированного ограничения количества адаптеров нет. Полный ответ должен помещаться в 32-битное поле длины IOCTL в байтах. |
| 12 | Количество работающих модулей | Число записей с флагом `Running`; `0..count`. |

При успешном выполнении далее следуют ровно `count` записей. Длина успешного ответа — **`16 + count * 1760`**; отсутствие модулей означает успешный ответ длиной 16 байт. Расчёты количества/длины проверяются относительно `UINT32_MAX`, а не настроенного предела адаптеров. Непустые входные данные вызывают `STATUS_INVALID_PARAMETER`. Буфер меньше 16 байт вызывает `STATUS_BUFFER_TOO_SMALL`. Буфер, вмещающий заголовок, но не **полный текущий снимок**, получает ровно 16-байтовый заголовок и `STATUS_BUFFER_OVERFLOW` (Win32 `ERROR_MORE_DATA`), а не частичный список адаптеров. Вычислите необходимую длину по этому заголовку, выделите буфер большего размера и повторите запрос; подключение/отключение может снова изменить необходимый размер. Снимком является только успешный полный ответ. Оба клиента начинают с умеренного буфера на 56336 байт, затем при необходимости увеличивают его, учитывая возможную ошибку выделения памяти и ограничивая число повторов при изменениях топологии; они никогда не выделяют заранее арифметически максимальный размер. Полные запросы могут завершиться с `STATUS_RETRY`, если частые изменения подключений не позволяют получить согласованный снимок; это не означает пустой список. Сохраняется действующее требование эксклюзивного доступа к устройству от Administrator/SYSTEM, в том числе после shutdown политики, пока дескриптор остаётся открытым.

Смещения записей указаны относительно каждой 1760-байтовой записи. C++ `AdapterInfo` содержит следующие поля; тип `Client::AdapterInfo` в клиенте из заголовочного файла предоставляет те же данные. Это владеющие декодированные типы, **а не** представления нативной структуры формата обмена:

| Смещение | Поля C++ | Формат обмена / источник |
|---:|---|---|
| 0 | `module_id` | `u64`, идентификатор модуля драйвера. |
| 8, 12, 16 | `interface_index`, `filter_interface_index`, `lower_interface_index` | Три `u32`: индексы интерфейса базового минипорта (совпадает с событиями соединения), фильтра и нижележащего интерфейса. |
| 20 | `flags` | `u32`, биты достоверности/состояния/усечения, указанные ниже. |
| 24, 32, 40 | `interface_luid`, `filter_interface_luid`, `lower_interface_luid` | Три `u64`, соответствующие значения NET_LUID. |
| 48 | `interface_guid` | 16 байт: порядок полей Windows GUID (`Data1:u32 LE`, `Data2:u16 LE`, `Data3:u16 LE`, `Data4[8]`). В C++ используется `std::array<uint8_t,16>`. |
| 64, 68 | `media_type`, `physical_medium` | Два `u32`, значения перечислений NDIS для среды / физической среды. |
| 72, 76 | `media_connect_state`, `media_duplex_state` | Два `u32`: состояние подключения неизвестно/подключено/отключено=`0/1/2`; дуплекс неизвестен/полудуплекс/полный дуплекс=`0/1/2`. |

| 96, 100, 104, 108 | `mtu`, `mac_options`, `supported_packet_filters`, `max_multicast_list_size` | Четыре `u32`, общие атрибуты перезапуска; MTU в байтах, значения параметров/фильтров являются битовыми масками. |
| 112, 120 | `max_xmit_link_speed`, `max_rcv_link_speed` | Два `u64`, общие максимальные скорости TX/RX в бит/с. |

| 144, 148, 152, 156 | `data_backfill_size`, `context_backfill_size`, `restart_flags`, `attach_flags` | Четыре `u32`: размеры backfill в байтах, общие флаги перезапуска, флаги подключения. |

| 224, 736, 1248 | `instance_name`, `base_name`, `filter_module_name` | Три массива UTF-16LE по 256 кодовых единиц: `BaseMiniportInstanceName`, `BaseMiniportName`, `FilterModuleGuidName`. | Флаг | Бит | Константа C++ `AdapterInfo::` |
|---|---:|---|
| Допуск открыт | `0x01` | `Running` |

| Доступно поле присутствия разъёма | `0x04` | `ConnectorPresentValid` |
| Имя экземпляра/базовое имя/имя модуля фильтра усечено | `0x08` / `0x10` / `0x20` | `InstanceNameTruncated` / `BaseNameTruncated` / `FilterModuleNameTruncated` |
| Получено указание состояния канала | `0x40` | `LinkStateValid` |
| Доступны причина/флаги приостановки | `0x80` | `PauseValid` |

Имена длиннее 255 единиц кода UTF-16 явно ограничиваются с соответствующим битом усечения; усечение никогда не разрезает суррогатную пару. Неизвестные числовые значения перечислений NDIS сохраняются. Клиенты проверяют версию схемы и размер записи, точную общую длину, количества, флаги, длину MAC-адреса и границы/терминаторы строк с подсчитанной длиной, прежде чем публиковать какой-либо результат. При ошибке снимок вызывающей стороны не меняется. `AdapterSnapshot` содержит `uint32_t running_count` и `std::vector<AdapterInfo> adapters`; пустой вектор имеет значение только после успешного запроса. Имена в мониторе кодируются в UTF-8 с экранированными управляющими байтами, а недоступные общие поля, поля разъёма и автосогласования помечаются как неизвестные, а не сообщаются как реальные нули.

### Уведомление о запуске драйвера

`Global\FirewallXNdisFilter.DriverReady` (имя ядра `\BaseNamedObjects\FirewallXNdisFilter.DriverReady`) — это именованное событие с ручным сбросом, отдельное от байтового потока устройства и IOCTL. Доступ к новым объектам разрешён только Administrator/SYSTEM. При запуске после инициализации управляющего устройства и таймера драйвер создаёт/открывает событие, сигнализирует его и сохраняет его дескриптор до выгрузки; при выгрузке событие сбрасывается и дескриптор закрывается. Драйвер предоставляет это уведомление независимо от монитора. Создание события предпринимается по возможности, если каталог глобальных объектов ещё недоступен во время ранней загрузки системы; инициализация устройства не зависит от успешности уведомления.

Клиент из заголовочного файла при запуске сбрасывает это событие, повторяет попытку открытия и затем ожидает сигнала, не опрашивая устройство. Сигнал — лишь подсказка для повторной попытки, а не доказательство присоединения NDIS, авторизации устройства или совместимости версии. Консольный монитор открывает уже доступное устройство; он не ожидает событие готовности, не загружает временный драйвер и не переподключается после завершения установленного сеанса.

### Методы клиента C++

Создавайте `Driver(std::wstring service_name = L"FirewallXNdisFilter")`; аргумент выбирает базовое имя устройства, а не службу, которую нужно создать. Класс некопируемый. Методы, возвращающие `bool`, сообщают об ошибках через `std::string& error`; отправка запроса не подразумевает синхронного ответа-события или подтверждения применения вердикта.

| Метод | Контракт |
|---|---|
| `bool Open(std::string& error)` | Открывает существующее устройство, сохраняя код ошибки Win32 в `GetLastError()`. Завершается ошибкой, если этот сеанс клиента уже открыт. Не устанавливает, не привязывает, не загружает и не согласует версию. |
| `bool GetVersion(uint8_t out[4], std::string& error)` | Читает четырёхбайтную версию; интеграции должны требовать `0.3.3.0`. |
| `bool GetFilteredDeviceCount(uint32_t& out, std::string& error)` | Синхронно читает снимок работающих модулей через `IOCTL_FILTERED_DEVICE_COUNT`. Требуются ровно четыре байта ответа. При ошибке возвращает false и оставляет `out` без изменений; неподдерживаемый запрос означает недоступность, а не ноль. |
| `bool GetAdapterInfo(AdapterSnapshot& out, std::string& error)` | Синхронно читает и проверяет полный снимок подключённых модулей переменного размера, описанный выше, увеличивая буфер запроса по необходимости. Включает неработающие модули; владеющие строки/массивы остаются действительными после возврата. Оставляет `out` без изменений при ошибке, включая некорректный вывод или ошибку выделения памяти. |
| `void Run(const Handlers& handlers, unsigned poll_interval_ms = 1000)` | Запускает поток чтения и блокирует выполнение до остановки или завершения потока чтения. Диспетчеризирует полные записи и вызывает `on_poll` в вызывающем потоке. Не запрашивает автоматически журналы/статистику и не отправляет вердикты. |
| `bool SendVerdict(uint64_t id, Verdict verdict, std::string& error)` | Отправляет один вердикт для ID ожидающего события. Принимаются только значения вердикта 2–7. |
| `bool RequestLogs(std::string& error)` | Отправляет `GetLogs`; существующие события журнала уже поставлены в очередь для чтения. |
| `bool RequestBandwidthStats(std::string& error)` | Запрашивает асинхронные записи трафика для активных накопителей. При отсутствии активных накопителей записи трафика не выдаются. |
| `bool RequestMemoryStats(std::string& error)` | Запрашивает диагностический `LogLine` со статистикой хранилища/счётчиков политики. |
| `bool RequestClearCache(std::string& error)` | Делает недействительными все записи постоянных вердиктов. Не отвечает на ожидающие NBL. |
| `bool RequestShutdown(std::string& error)` | Выполняет `IOCTL_SHUTDOWN`; не сигнализирует событие остановки `Run` и не закрывает дескриптор. |
| `void Stop()` | Сигнализирует `Run` и один раз запрашивает выключение. Безопасно вызывать из обратных вызовов или другого потока, пока активен `Run`. |
| `void Cleanup()` | Вызывает `Stop`, закрывает дескрипторы сеанса и сбрасывает анализатор записей. Дождитесь завершения/возврата из `Run`, прежде чем вызывать его или уничтожать объект. Деструктор также вызывает `Cleanup`. |
| `bool Install(const std::wstring& sys_path, std::string& error, bool inbound_udp_pid_fallback = true)` | Заглушка совместимости: всегда возвращает ошибку неподдерживаемой операции. Вместо этого используйте нативный установщик. Ни один аргумент не включает путь загрузки драйвера или резервный механизм PID. |

Типичная интеграция открывает устройство, проверяет его версию, устанавливает обработчики, отвечает на события `on_connection` и использует `on_poll` для периодических запросов и положительного ограничения времени работы. Вызовите `Stop`, дождитесь завершения `Run`, затем вызовите `Cleanup`. Держите обратные вызовы достаточно короткими, чтобы ответить до истечения времени ожидания.

### Легковесный клиент только с заголовочным файлом

[FirewallXNdisFilter.hpp](monitor/include/FirewallXNdisFilter.hpp) предоставляет отдельное пространство имён/API **`firewallxndisfilter::Client`**. Включите только этот файл в приложение Windows x64 **C++20**; исходные тексты `pmkext`, кодек и клиентская библиотека не нужны. Клиент использует Kernel32 и Advapi32 (MSVC связывает Advapi32 через pragma в заголовке; другие цепочки инструментов должны связать его явно). Скомпилированный пример — [callback_client.cpp](monitor/examples/callback_client.cpp), собираемый как `build/monitor/callback_client.exe`. Пример открывает реальное устройство, если его явно запустить; офлайн-тесты никогда его не запускают.

`Run` использует один поток, принадлежащий вызывающей стороне: он блокируется в ожидании завершения асинхронного чтения (overlapped), `Stop` или необязательного предельного времени выполнения. Автоматического таймера статистики или вердикта нет. Буфер приёма может расширяться для больших групп трафика; выделение памяти при этом может завершиться ошибкой. Заголовки подключений, полезные нагрузки, массивы данных о трафике и представления сообщений журнала заимствуют этот буфер и становятся недействительными после возврата обратного вызова; скопируйте данные, которые должны пережить обратный вызов. Обратные вызовы трафика выполняются один раз для каждой непустой групповой записи, а не один раз для каждого кортежа.

| Метод | Контракт (`DWORD`: 0 — успех, в противном случае ошибка Win32) |
|---|---|
| `Open()` | Обрабатывает ожидающий `Stop`, возвращая `ERROR_OPERATION_ABORTED` до обращения к устройству; в противном случае пытается открыть существующее эксклюзивное устройство Administrator/SYSTEM. Для эксклюзивного устройства `ERROR_SHARING_VIOLATION` немедленно возвращается при любой попытке; вызывающий может повторить попытку после того, как другой контроллер освободит свой дескриптор. После любой другой ошибки открытия создаёт/открывает защищённое событие `Global\FirewallXNdisFilter.DriverReady`, сбрасывает его перед повторной попыткой, затем ждёт **неограниченно**, без опроса устройства или тайм-аута запуска. Сигнал лишь запрашивает повторную попытку. `Stop()` отменяет это ожидание с `ERROR_OPERATION_ABORTED`. Никогда не устанавливает/не загружает драйвер. После открытия требует версию `{0,3,3,0}`; ошибки версии/I/O возвращаются, а не трактуются как сигналы запуска. |
| `Run(const Callbacks&, DWORD duration_ms = INFINITE)` | Блокирующая диспетчеризация обратных вызовов в вызывающем потоке. Положительная длительность ограничивает только мониторинг, **а не неограниченное ожидание запуска `Open`**; ноль недопустим. `Stop`/истечение времени выполнения приводит к успешному возврату после отмены незавершённого чтения и получения результата его завершения. Неожиданные чтения нулевых байтов являются ошибкой, а не циклом повторных попыток. Исключения обратных вызовов распространяются после получения результата завершения ожидающей операции ввода-вывода. |
| `Stop()` | Потокобезопасная локальная остановка, пригодная во время `Open`/`Run`; будит ожидание. Остановка, запрошенная в закрытом состоянии, один раз отменяет следующий `Open` с `ERROR_OPERATION_ABORTED` до обращения к устройству; успешный `Close` очищает ожидающую остановку. Сама по себе не выключает политику, не закрывает дескрипторы и не выгружает LWF. |
| `Close()` | Возвращает `ERROR_BUSY` во время `Run`. В противном случае закрывает дескрипторы; очистка устройства отключает политику и освобождает ожидающие пакеты через fallback. Дождитесь возврата `Run` и завершения всех остальных вызывающих перед `Close`/уничтожением. |
| `GetVersion(std::array<uint8_t,4>&)` / `GetFilteredDeviceCount(uint32_t&)` | Синхронные запросы IOCTL; точные четырёхбайтные ответы. Выходные значения не изменяются при ошибке. |
| `GetAdapterInfo(AdapterSnapshot&)` | Синхронный запрос снимка подключённых модулей переменного размера с автоматическим увеличением буфера, включая неработающие модули. Владеющие типы `Client::AdapterSnapshot` / `Client::AdapterInfo` имеют документированные выше поля и флаги действительности. Оставляет выход без изменений при ошибке; некорректные ответы возвращают `ERROR_INVALID_DATA`, ошибка выделения памяти возвращает `ERROR_NOT_ENOUGH_MEMORY`. |
| `SendVerdict(uint64_t id, Verdict)` | Отправляет фиксированный десятибайтный вердикт; допускаются только значения 2..7. Нет подтверждения применения вердикта. |
| `Send(Command)` | Однобайтные ClearCache=4, GetLogs=5, GetBandwidthStats=6 или PrintMemoryStats=7. Нет автоматических запросов статистики. |
| `Shutdown()` | Вызывает Stop и выполняет IOCTL выключения политики. Не закрывает, не выгружает и не отвязывает. |

`Callbacks` содержит необязательные указатели на функции и общий `context`:

| Обратный вызов | Аргументы после `void* context` |
|---|---|
| `on_connection_v4` | `const ConnectionV4* header, const uint8_t* payload, uint32_t payload_size` |
| `on_connection_v6` | `const ConnectionV6* header, const uint8_t* payload, uint32_t payload_size` |
| `on_log` | `uint8_t severity, std::string_view message` |
| `on_bandwidth_v4` | `uint8_t protocol, uint32_t interface_index, const BandwidthV4* entries, uint32_t count` |
| `on_bandwidth_v6` | `uint8_t protocol, uint32_t interface_index, const BandwidthV6* entries, uint32_t count` |

Каждый указатель заголовка/массива/полезной нагрузки ссылается непосредственно на проверенный входной буфер и становится недействительным после возврата обратного вызова. Таблица обратных вызовов и `context` должны оставаться действительными на протяжении `Run`. Обратные вызовы могут отправлять команды/вердикты или вызывать `Stop`; не закрывайте/не уничтожайте клиент из обратного вызова. `Open`/`Close` не являются конкурентными операциями; во время запуска поддерживается только `Stop`, а команды могут выполняться конкурентно после успешного `Open`. Медленные обратные вызовы всё так же задерживают вердикты и выключение.

| Упакованный тип (`Client::`) | Размер / поля в wire-порядке |
|---|---|
| `ConnectionV4` / `ConnectionV6` | 27 / 51 байт: `id:u64`, `interface_index:u32`, `direction:u8`, `protocol:u8`, `local_ip[4/16]`, `remote_ip[4/16]`, `local_port:u16`, `remote_port:u16`, `payload_layer:u8=3`. Следующая четырёхбайтная длина полезной нагрузки проверяется и передаётся отдельно с указателем на полный IP-пакет. |
| `BandwidthV4` / `BandwidthV6` | 28 / 52 байта на запись: `local_ip[4/16]`, `local_port:u16`, `remote_ip[4/16]`, `remote_port:u16`, `transmitted_bytes:u64`, `received_bytes:u64`. Групповой `interface_index:u32` находится в заголовке записи и передаётся отдельно в обратный вызов; один обратный вызов получает весь непрерывный массив. |

Эти фиксированные, тривиально копируемые wire-представления используют ограниченные областью видимости `#pragma pack(push, 1)` / `pop` с проверками размера, выравнивания и смещения во время компиляции. Все числа используют little-endian (native на поддерживаемой Windows x64); адреса остаются байтами в сетевом порядке. Читайте упакованные скалярные поля по значению; не передавайте адрес/ссылку поля API, ожидающему естественно выровненные целые числа. IPv4/IPv6 выбирается по типу обратного вызова, а не по добавленному полю `ipv6`; PID/ID потока отсутствует. Семантика направления и политики/fallback описана выше. `Verdict` содержит Accept=2, PermanentAccept=3, Block=4, PermanentBlock=5, Drop=6 и PermanentDrop=7.

Для офлайн-ответов адаптера `Client::DecodeAdapterInfo(Bytes, AdapterSnapshot&)` выполняет ту же проверку/декодирование с владением данными, что и `GetAdapterInfo`, без доступа к устройству. Его константы макета: `AdapterInfoVersion=1`, `AdapterInfoHeaderSize=16`, `AdapterInfoEntrySize=1760`, `AdapterNameCapacity=256` и `AdapterMacCapacity=32`. `MaxAdapters=(UINT32_MAX-16)/1760` и `MaxAdapterInfoSize=16+MaxAdapters*1760` — это границы арифметического переполнения, а не цели выделения памяти или настроенные квоты элементов; `InitialAdapterInfoSize=56336` — только начальная ёмкость запроса. Константы флагов `Client::Adapter*` соответствуют псевдонимам `AdapterInfo::` выше, при этом `AdapterKnownFlags=0xff`.

Для офлайн/пользовательских транспортов `Client::DispatchRecord(Bytes, callbacks)` проверяет одну полную запись, прежде чем предоставить какие-либо упакованные представления. Необязательный помощник `Client::Stream` предоставляет доступный для записи `Buffer()` (не более 65536 байт), `Commit(written, callbacks)`, `PendingBytes()` и `Reset()`; недействительный поток остаётся ошибочным до `Reset`. Заполните последний `Buffer` и вызовите `Commit` для него, прежде чем запрашивать другой; `Buffer` может уплотнить хранилище, поэтому не сохраняйте его указатель между вызовами. `MaxRecordSize=1048636` — граница кадра подключения, а `MaxPayloadSize=1048576` — граница полезной нагрузки подключения; хранилище данных о трафике увеличивается до полного размера группы с учётом возможной ошибки выделения памяти, `ReadSize=65536` — размер потокового фрагмента клиента, а не ограничение размера чтения драйвером. Драйвер никогда не создаёт события connection-END, и этот клиент их не предоставляет.

### Обратные вызовы и типы данных

Все члены `Handlers` необязательны:

| Обратный вызов | Аргумент / контекст выполнения |
|---|---|
| `on_connection` | `const Connection&`, в потоке чтения. Используйте `id` при отправке вердикта. |
| `on_connection_end` | `const ConnectionEnd&`, обратный вызов декодера совместимости в потоке чтения; этот драйвер никогда не создаёт соответствующие записи. |
| `on_log` | `const LogLine&`, в потоке чтения. |
| `on_bandwidth` | `const BandwidthStats&`, в потоке чтения. |
| `on_warning` | `const std::string&`, диагностика I/O/протокола на стороне клиента; может выполняться в потоке чтения или `Run`. Не является записью журнала драйвера. |
| `on_poll` | Без аргументов, в потоке, вызывающем `Run`, один раз на итерацию опроса. |

Аргументы обратного вызова временные; копируйте данные, необходимые после возврата обратного вызова. Синхронизируйте состояние, совместно используемое обратными вызовами чтения и `on_poll`.

| Тип | Открытые поля |
|---|---|
| `Connection` | `bool ipv6`; `uint64_t id`; `uint32_t interface_index`; `uint8_t direction, protocol`; `uint8_t local_ip[16], remote_ip[16]`; `uint16_t local_port, remote_port`; `uint8_t payload_layer`; `uint32_t payload_size`; `std::vector<uint8_t> payload`. |
| `ConnectionEnd` | `bool ipv6`; `uint64_t process_id`; `uint8_t direction, protocol`; `uint8_t local_ip[16], remote_ip[16]`; `uint16_t local_port, remote_port`. Нет ID вердикта или полезной нагрузки. |
| `LogLine` | `Severity severity`; `std::string message`. |
| `BandwidthEntry` | `bool ipv6`; `uint8_t local_ip[16]`; `uint16_t local_port`; `uint8_t remote_ip[16]`; `uint16_t remote_port`; `uint64_t transmitted_bytes, received_bytes`. |
| `BandwidthStats` | `uint8_t protocol`; `uint32_t interface_index`; `std::vector<BandwidthEntry> entries`. Индекс применяется к каждой записи в этой группе. |

Массивы IP содержат байты адресов в сетевом порядке. IPv4 использует первые четыре байта; декодер C++ оставляет оставшиеся байты нулевыми. `ipv6` выводится из типа записи, а не из отдельного wire-поля. `protocol` — номер IP-протокола, например 1=ICMP, 6=TCP, 17=UDP, 58=ICMPv6. Транспортные порты равны нулю там, где они недоступны/неприменимы. Разбор расширений IPv6 ограничен восемью заголовками и первыми 320 байтами наблюдаемого кадра NDIS. Для пакета с одним NB, чья цепочка расширений превышает любую из границ, `protocol` определяет первое неразобранное расширение, а порты остаются нулевыми; его захваченная IP-полезная нагрузка всё ещё полная, но неопознанный транспорт TCP/UDP не может участвовать в группах трафика TCP/UDP или постоянном кэшировании.

`Connection`, `ConnectionEnd` и `BandwidthEntry` предоставляют `LocalIpString()` и `RemoteIpString()`. `Connection::PayloadHexString()` создаёт шестнадцатеричную строку в нижнем регистре без разделителей. Дополнительные помощники: `FormatIpv4`, `FormatIpv6`, `NormalizeIpAddress`, `ProtocolToString`, `DirectionToString`, `PayloadLayerToString` и перегрузки `ToString` для `Verdict`, `Severity` и `InfoType`.

### Вердикты, тайм-ауты и кэширование

| `Verdict` | Байт | Эффект |
|---|---:|---|
| `Accept` | 2 | Разрешить этот NBL. |
| `PermanentAccept` | 3 | Разрешить и кэшировать решение для TCP/UDP-кортежа, когда его можно кэшировать; соответствующие попадания в кэш обновляют его TTL простоя. |
| `Block` | 4 | Молча отбросить этот NBL. |
| `PermanentBlock` | 5 | Отбросить и кэшировать решение для TCP/UDP-кортежа, когда его можно кэшировать. |
| `Drop` | 6 | Молча отбросить этот NBL; то же действие в пути данных, что и Block. |
| `PermanentDrop` | 7 | Отбросить и кэшировать решение для TCP/UDP-кортежа, когда его можно кэшировать. |

TCP RST или ICMP-ответ об отклонении не генерируются. `Undecided=0`, `Undeterminable=1`, `RedirectNameServer=8`, `RedirectTunnel=9`, `Failed=10` и `RedirectSplitTunnel=11` не принимаются как вердикты.

Для ожидающих решений установлен **срок по умолчанию 8000 мс**, отсчитываемый от классификации, а не от момента, когда приложение прочитало событие. Драйвер проверяет тайм-ауты каждую **1 секунду только при существовании ожидающих NBL**, поэтому действие по умолчанию может сработать приблизительно на один дополнительный интервал проверки позже дедлайна, плюс задержка планирования DPC. Вердикты всё равно проверяются по фактическому дедлайну и применяются немедленно, если действительны; они не ждут таймера. Резервное решение по умолчанию — **fail-closed (отбрасывание)** при отсутствии или отключении контроллера, завершении сеанса, тайм-ауте или ограничениях политики/очереди. Без контроллера подходящие транзитные IP-пакеты отбрасываются немедленно; при активном контроллере некэшированный пакет ожидает вердикт из пользовательского пространства до своего дедлайна и отбрасывается, если ответа нет. Исключения для локальных адресов и обход при недоступном списке адресов применяются до политики. Действительный кэшированный `PermanentAccept` всё ещё является явным решением пользовательского пространства и может допускать соответствующий трафик, пока этот сеанс остаётся активным. Отключение/завершение работы очищает эти кэшированные решения. Обход управляющих кадров не-IP не изменён. Пакеты отбрасываются при приостановленном или недействительном подключении фильтра, некорректных данных, неподдерживаемых метаданных копирования или небезопасном копировании, даже если явно настроен fail-open.

Постоянное решение — это **запись TTL-кэша только для TCP/UDP**, а не разрешение на время жизни сокета. **Каждый хостовый `interface_index` имеет четыре независимые динамически растущие хеш-таблицы: TCP/IPv4, UDP/IPv4, TCP/IPv6 и UDP/IPv6.** Настроенного максимального числа записей нет, как и вытеснения действующих решений, обусловленного ёмкостью. Другие IP-протоколы (включая ICMP/ICMPv6) никогда не создают и не используют постоянные записи: постоянный вердикт применяется только к этому NBL, а следующему пакету всё равно требуется решение.

Внутри каждой таблицы ключом является полный нормализованный кортеж `local_ip, local_port, remote_ip, remote_port`. Оба направления и разные VLAN совместно используют решение, когда кортежи совпадают **в пределах одного интерфейса, протокола и семейства IP**. Путь/направление NDIS, VLAN, ID модуля, эпоха и MAC-адреса Ethernet не различают записи. TCP и UDP, разные индексы интерфейсов и разные семейства IP используют отдельные кэши.

Просроченные записи немедленно перестают совпадать. Пока кэши непусты, драйвер автоматически запрашивает полный проход очистки истёкших записей каждые 10 секунд; монитору не нужно запрашивать очистку.

За исключением описанного выше предела в 1000 поставленных в очередь `LogLine`, ожидающие решения, очереди событий, хранилище трафика и данные копий приёма не имеют фиксированной квоты числа элементов или совокупного числа байтов. Исчерпание невыгружаемого пула может вызвать bugcheck машины. Счётчики трафика используют 64-битную арифметику с насыщением.

`PrintMemoryStats` ставит в очередь `LogLine` уровня Info, содержащую только количества элементов в коллекциях механизма политики:

| Поле | Количество |
|---|---|
| `pending` | Ожидающие NBL, ещё не захваченные для завершения, включая истёкшие или инвалидированные запросы, ожидающие завершения обработки. |
| `pending_nodes` | Выделенные узлы ожидания, включая захваченное решение, удерживаемое частично прочитанным событием. |
| `events` | События в очереди до постановки в очередь самого статистического `LogLine`, включая частично прочитанные события. |
| `interfaces` | Контексты интерфейсов, включая отсоединённые контексты, ожидающие высвобождения кэша. |
| `bandwidth` | Записи в активном и повторном хранилищах трафика; отсоединённый отчёт, находящийся в обработке, не включается, а повторные хранилища могут содержать дублирующиеся ключи. |
| `cached_tcp_v4`, `cached_udp_v4`, `cached_tcp_v6`, `cached_udp_v6` | Записи в каждом кэше протокола/семейства, суммированные по контекстам интерфейсов и текущим/предыдущим таблицам. Записи, ожидающие очистки по истечению срока или инвалидированию, включаются до их высвобождения. |

Это количества коллекций, а не размеры в байтах, ёмкости, счётчики трафика или полный учёт отсоединённого и ожидающего освобождения хранилища. Если запись кэша не удаётся вставить, текущий пакет всё равно получает запрошенный вердикт, но для последующего трафика потребуется новое решение.

Стандартный TTL равен **60000 мс**. `PermanentAccept` использует **скользящий тайм-аут простоя**: первоначальный дедлайн задаётся при применении вердикта, а каждый кэшируемый пакет TCP/UDP, фактически допущенный этой всё ещё действительной записью, сбрасывает дедлайн на время его классификации плюс `CacheTtlMs`. Любое направление обновляет совпадающий кортеж в таблице этого протокола; TCP-трафик не может обновить запись UDP и наоборот. Предварительные проверки кэша и некэшируемые пакеты не обновляют его. В момент дедлайна или после него пакету требуется новое решение, а не восстановление истёкшей записи. `PermanentBlock` и `PermanentDrop` сохраняют **фиксированный TTL с момента применения вердикта**; совпадающий трафик не продлевает их.

Фрагменты, offload- или неполные транспортные заголовки и NBL с несколькими NB не могут создавать или обновлять постоянные записи. Очистка кэша, а также новый или отключённый сеанс контроллера сбрасывают все четыре таблицы на каждом интерфейсе. Приостановка NDIS, инвалидация подключения фильтра или отсоединение также инвалидируют ожидающие ID и кэши этого интерфейса; другие интерфейсы сохраняют свои записи.

Необязательные значения службы `Parameters`, все типа `REG_DWORD`, считываются при загрузке SYS: `DecisionTimeoutMs=8000` (ограничивается диапазоном 100–60000), `CacheTtlMs=60000` (1000–300000) и `FailClosed=1` (по умолчанию; явное значение `0` включает fail-open для случаев отсутствия контроллера, тайм-аута и ограничений очереди). Это конфигурация драйвера, а не команды протокола.

Поздние, дублирующиеся, неизвестные, отменённые или уже завершённые ID являются безопасными пустыми операциями (no-op): успешная запись вердикта **не является подтверждением, что NBL всё ещё существовал**. Такие записи не создают записи кэша. Ответа на каждый отдельный вердикт нет.

### Кадрирование и компоновки событий

События используют явное побайтовое кодирование, а не нативную компоновку структур C++/Rust:

```text
[type:u8][body_size:u32 LE][body:body_size bytes]
```

Заголовок имеет пять байтов. `body_size` не включает заголовок. Полная запись **подключения** имеет размер не более **1048636 байт** (`1 MiB + 60`, префикс IPv6); префикс IPv4 имеет размер 36 байт. Записи журнала сохраняют отдельное ограничение в 512 байт. Записи трафика не имеют настроенного ограничения размера кадра или числа записей: их длины/количества должны помещаться в явные поля `u32`, а выделение памяти должно быть успешным. Все числовые поля, **включая порты**, имеют порядок little-endian. Байты IP-адресов имеют сетевой порядок. Заполнения или неявного терминатора строки нет. В приведённых ниже компоновках `A=4` для IPv4 и `A=16` для IPv6.

| `InfoType` | Байт | Компоновка тела / доступность |
|---|---:|---|
| `LogLine` | 0 | `[severity:u8][message:remaining bytes]`. |
| `ConnectionIpv4` | 1 | Компоновка подключения ниже, `A=4`. |
| `ConnectionIpv6` | 2 | Компоновка подключения ниже, `A=16`. |
| `ConnectionEndEventV4` | 3 | Компоновка END только для совместимости, `A=4`; никогда не выдаётся. |
| `ConnectionEndEventV6` | 4 | Компоновка END только для совместимости, `A=16`; никогда не выдаётся. |
| `BandwidthStatsV4` | 5 | Компоновка трафика ниже, `A=4`. |
| `BandwidthStatsV6` | 6 | Компоновка трафика ниже, `A=16`. |

**Тело подключения**, по порядку:

| Поле | Кодирование / значение |
|---|---|
| `id` | `u64`, ID вердикта ожидающего NBL. |
| `interface_index` | `u32`, индекс хостового адаптера (`BaseMiniportIfIndex`), а не индекс гостевого интерфейса. |
| `direction` | `u8`: хостовый приём=0 / хостовая отправка=1. |
| `protocol` | `u8`, номер IP-протокола. |
| `local_ip` | `A` необработанных байтов, наблюдаемый адрес источника при хостовом приёме или назначения при хостовой отправке. |
| `remote_ip` | `A` необработанных байтов, наблюдаемый адрес назначения при хостовом приёме или источника при хостовой отправке. |
| `local_port` | `u16`. |
| `remote_port` | `u16`. |
| `payload_layer` | `u8`, всегда 3. |
| `payload_size` | `u32`, полная длина наблюдаемого IP-пакета, не более 1048576. |
| `payload` | Ровно `payload_size` байтов, начиная с исходного IP-заголовка; захват никогда не сокращается. |

Размер тела равен `31 + payload_size` для IPv4 или `55 + payload_size` для IPv6; общий размер кадра соответственно равен `36 + payload_size` или `60 + payload_size`. Байты ID процесса или выравнивающее заполнение отсутствуют.

**Тело END для совместимости**, понимаемое клиентом, но не создаваемое LWF:

```text
[process_id:u64=0][direction:u8][protocol:u8]
[local_ip:A bytes][remote_ip:A bytes][local_port:u16][remote_port:u16]
```

Его размер тела равен 22 байтам для IPv4 или 46 байтам для IPv6. ID, payload и отметка времени отсутствуют.

**Тело журнала:** severity имеет значения `Trace=1`, `Debug=2`, `Info=3`, `Warning=4`, `Error=5`, `Critical=6` или `Disabled=7`. Остальное — сообщение без завершающего NUL; сообщения, генерируемые драйвером, имеют кодировку UTF-8. Максимальная длина сообщения — 506 байт. Статистика памяти — это обычные записи `LogLine` уровня Info, а не отдельный тип события.

**Тело трафика:**

```text
[protocol:u8][interface_index:u32][count:u32]
repeat count times:
  [local_ip:A bytes][local_port:u16]
  [remote_ip:A bytes][remote_port:u16]
  [transmitted_bytes:u64][received_bytes:u64]
```

Каждая запись имеет размер 28 байт для IPv4 или 52 байта для IPv6; размер тела равен `9 + count * entry_size` (37 байт для одной записи IPv4, 61 байт для одной записи IPv6). Драйвер выдаёт **все элементы для одного хостового интерфейса, протокола и семейства IP в одной записи**, без искусственного ограничения количества, ограничения в 1 MiB для кадра трафика или разбиения группы. Общий `interface_index` — индекс хостового адаптера в точке перехвата; он разделяет идентичные нормализованные кортежи на разных хостовых адаптерах и не повторяется для каждой записи. Размер тела и количество должны помещаться в свои поля `u32`. В отличие от записей подключения, за каждым адресом сразу следует его порт.

Учёт трафика подсчитывает **допущенные IP-байты TCP/UDP** во время активности контроллера, сгруппированные по хостовому `interface_index` и нормализованному кортежу. `transmitted_bytes` соответствует хостовому приёму, а `received_bytes` — хостовой отправке; они относятся к гостю только на подходящем адаптере, обращённом к гостю. Отключение отбрасывает накопленные данные, а при повторном подключении контроллера сбор начинается заново. Это дельты с момента создания накопителя или последней успешной постановки его отчёта в очередь командой `GetBandwidthStats`, а не накопительные итоги по сокету. Если полную группу не удаётся поставить в очередь, все её счётчики, не вошедшие в отчёт, сохраняются для более позднего запроса. Число различных накопителей не имеет фиксированного предела; счётчики байтов являются 64-битными, записи не содержат PID, а счётчики не доказывают доставку в пункт назначения.

### Команды и проверка операций записи

В отличие от событий, команды **не кадрированы**. Одна операция записи может объединять полные команды с ненулевым общим размером, помещающимся в собственную длину ввода-вывода Windows **DWORD/u32**; определяемого драйвером предела 64 KiB нет. Весь пакет проверяется до применения любой команды; некорректный/неподдерживаемый суффикс не даёт вступить в силу более ранним командам в этом пакете. Это синтаксическая проверка, а не транзакционное подтверждение идентификаторов активных событий.

| `CommandType` | Байт | Размер в wire-формате | Эффект |
|---|---:|---:|---|
| `Shutdown` | 0 | 1 | То же влияние на сеанс политики, что и `IOCTL_SHUTDOWN`. |
| `Verdict` | 1 | 10 | `[1:u8][id:u64 LE][verdict:u8]`. |
| `UpdateV4` | 2 | Не поддерживается | Отклоняется; компоновка обновления не реализована. |
| `UpdateV6` | 3 | Не поддерживается | Отклоняется; компоновка обновления не реализована. |
| `ClearCache` | 4 | 1 | Инвалидирует все записи постоянного кэша. |
| `GetLogs` | 5 | 1 | Пустая операция (no-op) для совместимости; записи журнала уже поставлены в очередь. |
| `GetBandwidthStats` | 6 | 1 | Ставит в очередь дельты трафика для активных накопителей. |
| `PrintMemoryStats` | 7 | 1 | Ставит в очередь `LogLine` уровня Info, содержащий количества элементов коллекций политики. |
| `CleanEndedConnections` | 8 | Не поддерживается | Отклоняется; очистка записей с истёкшим сроком выполняется автоматически. |

Однобайтные команды содержат только свой байт команды. Байт команды 8 не поддерживается, в том числе когда он следует за допустимыми в остальном командами; весь пакет отклоняется до вступления в силу любой команды. Результаты запросов считываются асинхронно из того же потока событий; идентификатора корреляции или отдельного подтверждения нет. Диагностические/статистические записи могут не ставиться в очередь, если данных нет или превышен предел размера.

Пустые/усечённые операции записи отклоняются с `STATUS_INVALID_PARAMETER`; неподдерживаемые значения команды/вердикта и неизвестные IOCTL используют `STATUS_NOT_SUPPORTED`. Второй контроллер отклоняется с `STATUS_SHARING_VIOLATION`. Запросы версии и количества отфильтрованных устройств с недостаточно большим выходным буфером используют `STATUS_BUFFER_TOO_SMALL`. Запрос количества отфильтрованных устройств отклоняет непустой ввод с `STATUS_INVALID_PARAMETER`. Клиент C++ проверяет команды локально до записи и сообщает об ошибках ввода-вывода Windows через `error`.

### Независимые от устройства вспомогательные средства кодека

`pmkext::wire` предоставляет `IsCompatibleVersion`, `DecodeFilteredDeviceCount`, `DecodeAdapterInfoHeader`, `DecodeAdapterInfo`, `IsSupportedVerdict`, `ValidateCommands`, `EncodeVerdict` и `DispatchRecord`. `DecodeAdapterInfoHeader(bytes, length, uint32_t& required_size, error)` проверяет префикс заголовка не менее 16 байтов, проверяет арифметику полей schema/count/running-count и вычисляет полный размер ответа без выделения памяти; при ошибке он оставляет `required_size` неизменённым и не проверяет следующие записи. `DecodeAdapterInfo(bytes, length, AdapterSnapshot&, error)` проверяет и декодирует ровно один полный снимок адаптеров, оставляя вывод неизменённым при ошибке. Его константы: `kIoctlAdapterInfo=0x9C40E00C`, `kAdapterInfoVersion=1`, `kAdapterInfoHeaderSize=16`, `kAdapterInfoEntrySize=1760`, `kAdapterNameCapacity=256`, `kMaxAdapters=(UINT32_MAX-16)/1760` и `kMaxAdapterInfoSize=16+kMaxAdapters*1760`; последние две являются границами арифметики проверяемой длины, а не размерами предварительного выделения или квотами элементов. `kInitialAdapterInfoSize=56336` является только начальной ёмкостью запроса. `IsCompatibleVersion` принимает ровно `kRequiredDeviceVersion={0,3,3,0}`; сам `Open` эту проверку не выполняет. `DecodeFilteredDeviceCount` требует ненулевой указатель на ответ длиной ровно четыре байта в little-endian и оставляет свой вывод неизменённым при ошибке. `EncodeVerdict` заполняет фиксированный десятибайтный массив; `DispatchRecord` проверяет ровно один полный кадр до вызова его обработчика.

`RecordStream::Feed(bytes, length, callback, error)` принимает произвольные границы чтения и вызывает callback для каждого полного кадра. `PendingBytes()` сообщает число буферизованных неполных байтов; `Reset()` отбрасывает буферизованное состояние. Некорректный заголовок или слишком большая запись подключения/журнала инвалидируют поток до сброса; он не угадывает новую границу. Поток собирает одну запись через произвольные чтения драйвера, при необходимости с возможностью отказа увеличивая хранилище в куче для групп трафика, превышающих предел кадра подключения. Константы: `kRecordHeaderSize=5`, `kConnectionIpv4PrefixSize=36`, `kConnectionIpv6PrefixSize=60`, `kMaxPayloadSize=1048576`, `kMaxRecordSize=1048636` (только кадры подключений), `kMaxLogRecordSize=512`, `kMaxCommandBatchSize=UINT32_MAX` и `kVerdictCommandSize=10`.
